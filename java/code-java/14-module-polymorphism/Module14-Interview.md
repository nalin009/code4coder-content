## MODULE 14: Polymorphism with Compile-Time vs Runtime Binding

---
---

Q1: Explain the difference between compile-time and runtime polymorphism with examples. When would you use each?
Answer:
Compile-time polymorphism is achieved through method overloading, where multiple methods share the same name but differ in parameter lists, resolved by the compiler at compile time based on method signatures. Runtime polymorphism is achieved through method overriding, where a child class provides a specific implementation of a parent method, resolved by the JVM at runtime based on the actual object type using dynamic method dispatch.
Use compile-time polymorphism when you need different behaviors for the same operation based on different input types within the same class, such as a Calculator with add(int, int) and add(double, double). Use runtime polymorphism when you need different implementations across related classes in an inheritance hierarchy, such as different payment processors (CreditCard, PayPal, Crypto) all implementing a common processPayment() interface, allowing flexible behavior based on the actual object at runtime.

Q2: How does the JVM resolve method calls using dynamic method dispatch? Explain the role of the vtable.
Answer:
When the JVM encounters an invokevirtual instruction for an instance method call, it performs dynamic method dispatch using a vtable (virtual method table). Each class has a vtable stored in Metaspace containing pointers to all its virtual methods (non-static, non-final, non-private). When a method is called on an object reference, the JVM follows the reference to the actual object in the heap, retrieves the object's class metadata pointer, accesses that class's vtable, looks up the method at the appropriate index, and executes the found implementation.
This mechanism enables runtime polymorphism because even if the reference type is a parent class, the vtable belongs to the actual object's class (potentially a child class with overridden methods), ensuring the correct overridden method is executed. The vtable is shared by all instances of a class, making this approach memory-efficient despite the slight runtime overhead of pointer indirection.

Q3: Can you override a static method in Java? Why or why not? What is method hiding?
Answer:
No, you cannot override a static method in Java because static methods are bound to the class, not to instances, and are resolved at compile time based on the reference type rather than runtime based on the object type. When a child class defines a static method with the same signature as a parent class static method, it's called method hiding, not overriding.
Method hiding means the child class's static method hides the parent's static method, but which method gets called is determined by the reference type at compile time, not polymorphically at runtime. For example, if Parent p = new Child() and both have static method display(), calling p.display() invokes Parent's version regardless of the actual object being a Child instance. This violates polymorphic behavior and is fundamentally different from method overriding, where the object type determines which method executes.

Q4: What are covariant return types? Provide an example and explain why they were introduced in Java 5.
Answer:
Covariant return types, introduced in Java 5, allow an overriding method in a child class to return a subtype (more specific type) of the return type declared in the parent method, instead of requiring the exact same return type. For example, if a parent method returns Number, the overriding child method can return Integer (since Integer is a subtype of Number).
This feature was introduced to enable more specific return types in child classes without requiring client code to perform explicit casts, improving API usability and type safety. A common use case is in fluent interfaces and builder patterns where method chaining benefits from returning the specific child type rather than the generic parent type, allowing access to child-specific methods without casting. Covariant return types only work with reference types, not primitives, and this behavior remains unchanged through Java 25.

Q5: Explain the method resolution algorithm for overloaded methods. What is the priority order the compiler follows?
Answer:
When the compiler encounters a call to an overloaded method, it follows a specific priority algorithm to select the correct method. First, it looks for an exact type match with the argument types. If no exact match exists, it attempts widening primitive conversion (byte → short → int → long → float → double or char → int) to find a match. If still no match, it tries autoboxing or unboxing between primitives and wrapper classes.
Next, it attempts widening reference conversion by checking if the argument can be widened to a superclass or interface. Finally, as a last resort, it matches variable-length argument (varargs) methods. If no match is found at any level or multiple equally specific matches exist (ambiguity), a compilation error occurs. This algorithm ensures the most specific, appropriate method is selected while maintaining type safety and predictable behavior.

Q6: What are the rules for exception handling when overriding methods? Can you throw a broader checked exception in the child class?
Answer:
When overriding a method, the child class method cannot throw new or broader checked exceptions than the parent method declares, though it can throw fewer exceptions, narrower exceptions (subtypes of the parent's declared exceptions), or any unchecked exceptions (RuntimeException and its subclasses). This rule ensures that code written against the parent class interface doesn't encounter unexpected checked exceptions when working with child class objects, maintaining the Liskov Substitution Principle.
For example, if the parent method declares throws IOException, the child can throw FileNotFoundException (a subtype) or omit the throws clause entirely, but cannot throw SQLException (unrelated checked exception) or Exception (broader supertype). Unchecked exceptions can always be thrown because they don't require declaration and typically represent programming errors rather than recoverable conditions.

Q7: Why does instanceof return false for null? Is this behavior consistent across all Java versions including Java 25?
Answer:
The instanceof operator returns false for null references by design to provide null-safe type checking without throwing NullPointerException, allowing developers to safely check types without preceding null checks. This behavior is intentional because null doesn't represent an instance of any type; it's the absence of an object. The expression (null instanceof AnyType) always evaluates to false regardless of the type.
This behavior has been consistent since Java's inception and remains unchanged through Java 25, including with the introduction of pattern matching for instanceof in Java 16. The pattern matching feature also handles null consistently: if (obj instanceof String s) will not execute the if-block when obj is null, and the pattern variable s won't be assigned, maintaining the same null-safe semantics while reducing boilerplate code.

Q8: What is the Liskov Substitution Principle (LSP) and how does it relate to method overriding in Java?
Answer:
The Liskov Substitution Principle states that objects of a subclass should be substitutable for objects of their superclass without breaking the correctness of the program, meaning child class objects must honor the behavioral contract established by the parent class. In Java method overriding, this principle manifests in several rules: overriding methods cannot be more restrictive in access, cannot throw broader checked exceptions, must maintain the same functional behavior, and should preserve the parent method's preconditions and postconditions.
Violating LSP leads to fragile code where polymorphic substitution causes unexpected behavior or exceptions. For example, if a parent class's withdraw() method never throws IllegalArgumentException for positive amounts, the child class override shouldn't introduce this exception, as code written against the parent interface wouldn't be prepared to handle it. Java's compiler enforces some LSP aspects (access modifiers, checked exceptions) but cannot verify behavioral contracts, which require careful design and documentation.

Q9: How does the JIT compiler optimize polymorphic method calls? What is inline caching and monomorphic optimization?
Answer:
Modern JVMs use sophisticated optimizations for polymorphic method calls through the JIT (Just-In-Time) compiler. Inline caching involves the JIT remembering which concrete class was seen at each polymorphic call site and generating optimized code based on observed behavior. For monomorphic call sites (where only one concrete type is ever seen), the JIT can devirtualize the call entirely, converting it to a direct method call and potentially inlining the method body, eliminating vtable lookup overhead completely.
For bimorphic sites (two types observed), the JIT generates a fast type check with two inlined paths. For megamorphic sites (many types), it falls back to standard vtable dispatch. These optimizations mean that in real-world applications, well-designed polymorphic code performs nearly as well as static method calls after JIT warmup. Profiling data drives these optimizations, so code patterns that repeatedly use the same types benefit most, which is common in production systems where specific implementations dominate at particular call sites.

Q10: When would you use instanceof in production code, and when should you avoid it? What are the alternatives?
Answer:
You should use instanceof in specific scenarios: implementing the equals() method to check argument types before casting, working with library code where you don't control the class hierarchy, handling heterogeneous collections where objects of different types are legitimately stored together, and in performance-critical code where polymorphic dispatch measurably impacts performance (rare). It's also necessary when implementing visitor patterns or handling deserialization where type checking is unavoidable.
However, avoid excessive instanceof checks as a substitute for polymorphism, such as long chains of if-else type checking, which violates the Open/Closed Principle and creates brittle code. Instead, use polymorphic method overriding where each class implements its own behavior, or employ design patterns like Strategy or Command. The pattern matching enhancement in Java 16+ improves instanceof ergonomics but doesn't change the fundamental principle: if you find yourself frequently checking types, consider whether polymorphism or composition would better solve your design problem.

Q11: Explain the difference between method overriding and method hiding. How do instance variables behave in inheritance?
Answer:
Method overriding occurs with instance methods where a child class provides a specific implementation of a method defined in its parent, resolved at runtime based on the actual object type through dynamic dispatch. Method hiding occurs with static methods where a child class defines a static method with the same signature as the parent, resolved at compile time based on the reference type, not the object type, with no polymorphic behavior. Instance variables are never overridden or hidden; they are shadowed, meaning both parent and child variables exist simultaneously, with the reference type determining which variable is accessed.
For example, if Parent and Child both have an int value field, and you have Parent p = new Child(), accessing p.value retrieves the Parent's field, not the Child's, because variable access is resolved at compile time based on reference type. This is fundamentally different from method overriding where the object type determines behavior. Best practice is to avoid reusing variable names across inheritance hierarchies and use getter methods for polymorphic access to state.

Q12: How would you design a payment processing system using polymorphism? What are the benefits over using conditionals?
Answer:
Design a payment processing system with a PaymentProcessor interface defining the processPayment() method, then create concrete implementations (CreditCardProcessor, PayPalProcessor, CryptoProcessor, etc.) that each provide specific payment logic. The client code depends only on the PaymentProcessor interface, not concrete implementations, using dependency injection to receive the appropriate processor at runtime. This follows the Strategy pattern and allows adding new payment methods without modifying existing code (Open/Closed Principle).
Benefits over conditional approaches include: easier testing through mocking interfaces, no need to modify core logic when adding payment types, better separation of concerns with each processor encapsulating its own logic, and elimination of long if-else or switch chains that become maintenance nightmares. The polymorphic approach also enables runtime configuration (selecting processor based on user preference or geographic location) and concurrent evolution of payment implementations without coordination between teams, crucial in microservices architectures where different teams own different payment integrations.

NEW Q13: You discover a production bug where payments are being processed with the wrong processor. The code looks correct. How would you debug this polymorphism issue?
Answer (5+ YOE):
First, I would add logging to capture the actual object type at runtime using getClass().getName() at the point of processor selection and at the processPayment call site to verify the reference and object types match expectations. Next, I would check if the processor is being instantiated in a factory or dependency injection container - misconfigurations in Spring beans or factory logic often cause wrong implementations to be injected.
I would review the call stack in production logs or APM tools (NewRelic, Datadog) to trace where the processor instance originates. Check for shared mutable state - if processors are singletons but maintain state, concurrent requests might cause processors to interfere with each other. Use a debugger with conditional breakpoints on the reference variable to inspect its actual class at runtime. Finally, check for recent code changes in factories, constructors, or DI configurations that might have introduced the bug. In one real incident, a Spring @Primary annotation was added to the wrong bean, causing all autowired processors to use the wrong implementation.

NEW Q14: How do you balance polymorphism with performance in high-throughput systems (100K+ requests/second)?
Answer (5+ YOE):
In high-throughput systems, polymorphism is rarely the bottleneck - network I/O, database queries, and serialization typically dominate. However, when polymorphism is in a critical path with millions of iterations per request, optimization strategies include: ensuring call sites are monomorphic (same type every time) by splitting code paths, using final classes where inheritance isn't needed to enable JIT devirtualization, and considering manual dispatch tables for extremely hot paths in financial trading or gaming engines.
Profile first using JMH benchmarks and production profilers (YourKit, async-profiler) to identify megamorphic call sites. If a call site shows up hot in flame graphs, consider refactoring to eliminate unnecessary polymorphism or using specialized implementations. For example, separate fast paths for common cases from slow paths for edge cases. Monitor JIT compilation logs (-XX:+PrintCompilation) to see if methods are being de-optimized due to megamorphism. In practice, at one e-commerce company handling 200K req/sec, we found database connection pooling and JSON parsing were 1000x more impactful than polymorphic dispatch optimization.

NEW Q15: Explain a scenario where overriding equals() and hashCode() incorrectly broke polymorphism in production.
Answer (5+ YOE):
At a financial services company, we had a Transaction class hierarchy where BaseTransaction defined equals() using getClass() instead of instanceof. This worked initially, but when we introduced SpecialTransaction extends BaseTransaction, HashMap and HashSet started misbehaving. Lookup operations failed because a BaseTransaction key couldn't find a SpecialTransaction value even though they represented the same transaction.
The root cause was equals() symmetry violation: baseTransaction.equals(specialTransaction) returned false due to getClass() check, even when all fields matched. This violated the equals() contract and broke HashMap's internal logic. The fix was changing equals() to use instanceof and ensuring both classes used the same fields for equality. We also added comprehensive equals/hashCode unit tests for all subclasses. This taught us that value objects in inheritance hierarchies should either use composition instead of inheritance, or carefully design equals() with instanceof, or make the base class final to prevent problematic subclassing.

NEW Q16: How does polymorphism interact with Java's type erasure and generics?
Answer (5+ YOE):
Java's type erasure affects polymorphism in subtle ways. Generic type parameters are erased at runtime, so List<String> and List<Integer> both become List in bytecode. This means you cannot overload methods that differ only in generic types: void process(List<String> list) and void process(List<Integer> list) cause compilation errors because after erasure both become void process(List list).
However, polymorphism within generics works fine - if you have List<Animal> and populate it with Dog and Cat objects, polymorphic method calls like animal.makeSound() work as expected because the actual objects retain their runtime type information. Type erasure only affects the generic type parameters, not the object types themselves. One production gotcha: using raw types (List instead of List<T>) silences warnings and can lead to ClassCastException at runtime when polymorphism mixes with unchecked casts. Always use parameterized types and avoid raw types except when interfacing with legacy code.

NEW Q17: Describe how you'd refactor a large if-else chain checking instanceof into a polymorphic design.
Answer (5+ YOE):
Given a method with a long instanceof chain like: if (obj instanceof TypeA) {...} else if (obj instanceof TypeB) {...}, the refactoring process involves: First, identify the common operation being performed - this becomes an interface method (e.g., process(), handle(), execute()). Create an interface or abstract class with this method. Second, for each instanceof branch, create or modify the corresponding class to implement the interface with the branch logic moved into the overridden method.
Third, replace the entire if-else chain with a single polymorphic call: obj.process(). Fourth, if the classes can't implement the interface directly (e.g., they're from external libraries), use the Adapter pattern to wrap them. Example: a report generator with instanceof checks for PDF, Excel, CSV became interface ReportGenerator { void generate(Data data); } with PdfReportGenerator, ExcelReportGenerator, CsvReportGenerator implementations. The main code simplified from 50 lines of conditionals to: reportGenerator.generate(data). Add factories or DI to select the right implementation at runtime. Benefits: easier to test (mock), easier to extend (new types don't modify existing code), and clearer intent.

NEW Q18: What are the security implications of polymorphism in Java applications?
Answer (5+ YOE):
Polymorphism can introduce security vulnerabilities if not handled carefully. One common issue is object substitution attacks where attackers provide malicious subclass instances to APIs expecting parent types. If a method accepts a generic InputStream but the attacker provides a custom subclass that logs all read data, sensitive information can leak. Always validate that objects are of expected types in security-critical code, especially when deserializing user input.
Another risk is method override vulnerabilities where subclasses override security-sensitive methods unsafely. If a parent class's validatePermission() method is overridable, a malicious subclass could override it to always return true. Mark security-sensitive methods as final to prevent overriding. In authentication systems, we've seen cases where custom UserDetailsService implementations in Spring Security had bugs in equals() overrides that caused authentication bypasses. Use SecurityManager restrictions and sealed classes (Java 15+) to control which classes can extend security-critical hierarchies. Always perform security reviews on any code that accepts polymorphic types from untrusted sources, especially in deserialization, reflection, and plugin architectures.
