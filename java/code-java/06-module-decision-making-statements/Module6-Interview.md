## Module 6: DECISION-MAKING STATEMENTS

Q1. What is the difference between if-else and switch statements? When should you use each?
Answer:
The if-else statement evaluates boolean conditions and can handle ranges, complex expressions, and relational operators, making it highly flexible for any conditional logic. The switch statement works only with discrete values (int, char, String, enum) and internally uses lookup tables (tableswitch) or binary search (lookupswitch), providing O(1) or O(log n) performance. For 1-3 conditions, both perform similarly, but for 5+ discrete values, switch is faster and more readable. Use if-else for range checks, complex boolean logic, or conditions with AND/OR operators. Use switch for multiple discrete values, menu systems, or state machines where performance and maintainability matter.

Q2. Explain short-circuit evaluation in Java with an example. Why is it important?
Answer:
Short-circuit evaluation means that in logical AND (&&) and OR (||) operations, Java doesn't evaluate the second operand if the result is already determined by the first operand. For &&, if the first operand is false, the second is skipped because the overall result must be false. For ||, if the first operand is true, the second is skipped because the overall result must be true. This is crucial for null safety: if (obj != null && obj.isValid()) prevents NullPointerException because obj.isValid() is never called if obj is null. It also improves performance by avoiding unnecessary evaluations and allows writing cleaner, safer code without nested null checks.

Q3. Why doesn't Java support long, float, double, or boolean in switch statements?
Answer:
The switch statement was designed for discrete, exactly comparable values that can be efficiently mapped using lookup tables or binary search. Floating-point types (float, double) are excluded because they involve precision issues and cannot be reliably compared for exact equality due to rounding errors. The long type was likely excluded for simplicity, consistency with C/C++, and to encourage use of more appropriate types. Boolean has only two values (true/false), making if-else far more natural and readable than switch. This design prioritizes performance, clarity, and prevents subtle bugs from floating-point comparisons. These limitations remain unchanged through Java 25, though pattern matching (Java 21+) expands switch capabilities in other ways.

Q4. What are switch expressions (Java 14+)? How do they differ from traditional switch statements?
Answer:
Switch expressions, introduced in Java 14, allow switches to return values directly and use arrow syntax (->) that prevents fallthrough. Unlike traditional switch statements which execute code and require break to prevent cascading execution, switch expressions are expressions that evaluate to a value and can be assigned directly to variables. They eliminate the need for break statements using arrow syntax, must be exhaustive (handle all possible values), and use the yield keyword for multi-line case blocks that return values. This makes code more concise, safer (no fallthrough bugs), and more functional in style, while enabling better compile-time checking for exhaustiveness especially with enums.

Q5. What is the ternary operator? When should you use it, and when should you avoid it?
Answer:
The ternary operator (condition ? expression1 : expression2) is a compact inline way to express simple if-else logic that returns a value. It evaluates a boolean condition and returns one of two values based on the result, making it ideal for simple variable assignments, conditional returns, or setting default values. Use it when the logic is straightforward, involves a single condition, and fits on one line for readability. Avoid it for complex conditions with multiple AND/OR operators, nested ternary operations that hurt readability, side effects like method calls or print statements, or any situation where if-else would be clearer. The ternary operator is an expression (returns a value), while if-else is a statement (executes code).

Q6. Explain fallthrough behavior in switch statements. How can you prevent it?
Answer:
Fallthrough occurs in traditional switch statements when a case block doesn't end with break, causing execution to continue into subsequent cases without checking their conditions. This happens because switch internally jumps to the matching case and continues until encountering a break, return, or the end of the switch block. While usually unintended and causing bugs, fallthrough can be useful for multiple cases sharing the same logic. To prevent fallthrough, always include a break statement at the end of each case, use switch expressions (Java 14+) with arrow syntax which prevent fallthrough automatically, or add explicit comments like // fallthrough intentional to document deliberate use for code reviewers and maintainability.

Q7. How does the JVM optimize switch statements internally? What are tableswitch and lookupswitch?
Answer:
The JVM optimizes switch statements based on case value density. For densely packed cases with few gaps (like 1, 2, 3, 4, 5), the compiler generates tableswitch bytecode that creates an array-based lookup table enabling direct O(1) jumps to the matching case using the value as an array index. For sparse cases with many gaps (like 1, 100, 1000, 10000), it generates lookupswitch bytecode that performs binary search on sorted case values for O(log n) lookup time. Both strategies are significantly faster than if-else chains which check conditions sequentially in O(n) time. The compiler automatically chooses the optimal strategy based on case distribution, making switch substantially faster than if-else for 5+ cases without requiring developer intervention.

Q8. What is the difference between == and equals() when comparing strings?
Answer:
The == operator compares object references (memory addresses), checking if two variables point to the exact same object in memory. The equals() method compares object content, checking if two objects have the same value regardless of their memory location. For strings, == returns true only if both variables reference the same String object in the string pool, while equals() returns true if the character sequences are identical. Always use equals() for string comparison in conditional logic. A defensive technique called "Yoda conditions" places the literal first like "John".equals(name) to prevent NullPointerException if name is null, since literals are never null while variables might be.

Q9. What is pattern matching for switch (Java 21+)? Provide an example.
Answer:
Pattern matching for switch, introduced in Java 21, allows type checking and casting in a single step within switch expressions, eliminating explicit instanceof checks and casts. Instead of checking types separately, you can match against type patterns directly in case labels, with automatic type inference for the matched variable. For example, case String s -> "Length: " + s.length(); automatically checks if the value is a String and assigns it to variable s for use in the case block. This feature also supports null cases explicitly with case null ->, making null handling cleaner and type-safe. It represents Java's evolution toward more expressive, type-safe code while reducing boilerplate and enabling better compile-time checking, particularly useful for processing heterogeneous collections or implementing visitor patterns.

Q10. Explain the concept of exhaustiveness in switch expressions. Why is it important?
Answer:
Exhaustiveness means that a switch expression must handle every possible value of its input type, either through explicit case labels or a default case. Unlike switch statements which can omit cases (doing nothing for unmatched values), switch expressions must return a value for all inputs to ensure type safety and prevent compilation errors. For enums, the compiler enforces that all enum constants are covered or a default is provided. For primitive types and Strings, a default case is mandatory. This compile-time checking prevents runtime errors from unhandled values, makes code more robust and maintainable, and clearly documents all expected scenarios. It's particularly valuable for enums where adding a new constant forces review of all related switches, preventing bugs when requirements evolve.

Q11. What are the best practices for writing clean, maintainable decision-making code?
Answer:
Always use braces even for single-line if statements to prevent bugs when adding statements later. Prefer switch expressions over traditional switch (Java 14+) for cleaner syntax without fallthrough bugs. Use switch instead of long if-else chains for 5+ discrete values due to better performance and readability. Keep ternary operators simple and use them only for straightforward assignments; prefer if-else for complex conditions or side effects. Always include a default case in switch statements for defensive programming and logging unexpected values. Extract complex boolean conditions into well-named methods to improve readability and testability. Use short-circuit evaluation for null safety and performance. Prefer positive conditions over negative ones for clarity. Avoid deep nesting beyond three levels by using early returns or extracting methods. Document intentional fallthrough in switch statements with explicit comments.

Q12. How would you refactor a switch statement with 20+ cases into more maintainable code?
Answer:
For 20+ cases, consider using a Map-based approach where keys map to functional interfaces or lambda expressions representing the action for each case, enabling O(1) lookup and cleaner separation of concerns. Alternatively, implement the Strategy pattern with separate classes for each case behavior, improving testability and following Single Responsibility Principle. For related cases, use switch expressions with grouped cases like case 1, 2, 3 -> handleGroup1() to reduce duplication. If cases represent state transitions, consider implementing a state machine with explicit state classes. For enum-based switches, ensure exhaustiveness and document the purpose of each case. Extract case logic into separate methods with descriptive names. If the switch controls business logic, consider using a rule engine or decision table for better configurability and maintainability, especially if non-developers need to modify behavior.
